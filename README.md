### 1. База данных

Если PostgreSQL ещё не запущен, проще всего поднять его в Docker

```bash
docker run -d --name tensor_db \
  -e POSTGRES_USER=tensor \
  -e POSTGRES_PASSWORD=tensor \
  -e POSTGRES_DB=tensor \
  -p 3333:5432 \
  postgres:10
```

Явки указываются в .env файле, описание приведено ниже:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DB_USER` | `tensor` | пользователь PostgreSQL |
| `DB_PWD` | `tensor` | пароль |
| `DB_HOST` | `127.0.0.1` | хост |
| `DB_PORT` | `3333` | порт |
| `DB_NAME` | `tensor` | имя базы |
| `FILE_PATH` | `data/people.json` | путь к JSON с данными |

### 3. Запуск

В этом режиме приложение будет интерактивно ожидать ввода id сотрудника:
```
python main.py
```
При первом запуске приложение само создаст таблицу `employees`, индекс по
`parent_id` и загрузит данные из `data/people.json`. Повторный импорт не
выполняется, если таблица уже заполнена.

В этом режиме приложение выведет результат и прекратит выполнение:

```
python main.py --employee_id 3
```

В этом режиме приложение очистит таблицу:
```
python main.py --reset
```

### 4. Анализ запроса

Задача решается двумя обходами дерева в одном запросе:

```text
1. ancestors   — от сотрудника вверх по parent_id до офиса (type = 1)
2. office      — id найденного офиса
3. office_tree — от офиса вниз по parent_id по всему поддереву
4. финальный SELECT — из поддерева берутся только type = 3, сортировка по name
```

Первый обход останавливается, когда доходит до записи с `type = 1`:

```sql
WHERE a.type != 1
```

Так офис попадает в результат, но выше него рекурсия не идёт, даже если в
данных случайно окажется родитель над офисом.

Второй обход не ограничен глубиной вложенности отделов: структура
«отдел внутри отдела» (в тестовых данных — `id = 12` и `16` внутри `11`)
обрабатывается корректно.

Сортировка `ORDER BY name` выбрана осознанно: она даёт тот же порядок, что в
примере задания (`Иванов`, `Сидоров`, `Петров`), и делает вывод
детерминированным.

#### Сложность


На каждом шаге рекурсии выполняется `e.id = a.parent_id`, то есть поиск по
первичному ключу. Это Index Scan по B-дереву:

- один шаг — `O(log N)`;
- весь подъём — `O(h · log N)`;
- в памяти хранится `O(h)` строк.

`h` — это высота дерева, а не размер таблицы, поэтому первый обход дешёвый
при любой структуре данных.

Просмотр `h + 1` строк `ancestors` с фильтром `type = 1`:

- `O(h)`.

Рекурсивный шаг соединяет таблицу с рабочим множеством по
`e.parent_id = t.id`.

**С индексом по `parent_id`:** на каждую строку поддерева выполняется
Index Scan, итого

- `O(S · log N)`.

**Без индекса по `parent_id`:** индекс использовать нечем, и PostgreSQL
перечитывает всю таблицу на каждой итерации рекурсии. В замерах планировщик
выбрал Hash Join + Seq Scan всей таблицы за итерацию:

- `O(D · N + S)` при Hash Join;
- в худшем случае (Nested Loop с Seq Scan, например при вырожденном дереве)
  — `O(S · N)`.
