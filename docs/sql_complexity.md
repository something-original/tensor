# Сложность SQL-выборки и перспективы оптимизации

## 1. Обозначения

| Обозначение | Значение |
| --- | --- |
| `N` | число строк в таблице `employees` |
| `h` | высота пути от сотрудника до офиса (число предков) |
| `S` | число узлов в поддереве офиса (офис + все отделы + все сотрудники) |
| `k` | число сотрудников в офисе (`k ≤ S`) |
| `D` | число уровней в поддереве офиса (для плоской структуры «офис → отдел → сотрудник» `D = 3`) |

## 2. Исследуемый запрос

```sql
WITH RECURSIVE ancestors AS (
    SELECT id, parent_id, type, 0 AS depth
    FROM employees
    WHERE id = %(employee_id)s

    UNION ALL

    SELECT e.id, e.parent_id, e.type, a.depth + 1
    FROM employees AS e
    JOIN ancestors AS a ON e.id = a.parent_id
    WHERE a.type <> 1
      AND a.depth < 100
),
office AS (
    SELECT id FROM ancestors WHERE type = 1 LIMIT 1
),
office_tree AS (
    SELECT id, parent_id, name, type, 0 AS depth
    FROM employees
    WHERE id IN (SELECT id FROM office)

    UNION ALL

    SELECT e.id, e.parent_id, e.name, e.type, t.depth + 1
    FROM employees AS e
    JOIN office_tree AS t ON e.parent_id = t.id
    WHERE t.depth < 100
)
SELECT name
FROM office_tree
WHERE type = 3
ORDER BY id;
```

## 3. Пошаговый разбор

### 3.1 `ancestors` — подъём к офису

На каждом шаге рекурсии выполняется `e.id = a.parent_id`, то есть поиск по
первичному ключу. Это Index Scan по B-дереву:

- один шаг — `O(log N)`;
- весь подъём — `O(h · log N)`;
- в памяти хранится `O(h)` строк.

`h` — это высота дерева, а не размер таблицы, поэтому первый обход дешёвый
при любой структуре данных.

### 3.2 `office`

Просмотр `h + 1` строк `ancestors` с фильтром `type = 1`:

- `O(h)`.

### 3.3 `office_tree` — спуск по поддереву офиса

Рекурсивный шаг соединяет таблицу с рабочим множеством по
`e.parent_id = t.id`.

**С индексом по `parent_id`:** на каждую строку поддерева выполняется
Index Scan, итого

- `O(S · log N)`.

**Без индекса по `parent_id`:** индекс использовать нечем, и PostgreSQL
перечитывает всю таблицу на каждой итерации рекурсии. В замерах планировщик
выбрал Hash Join + Seq Scan всей таблицы за итерацию:

- `O(D · N + S)` при Hash Join;
- в худшем случае (Nested Loop с Seq Scan, например при вырожденном дереве)
  — `O(S · N)`.

Именно поэтому индекс по `parent_id` критичен: без него время запроса растёт
вместе с размером **всей** таблицы, а не только офиса.

### 3.4 Финальная выборка и сортировка

- фильтр `type = 3` — `O(S)`;
- `ORDER BY id` — сортировка `k` строк, `O(k · log k)`, память `O(k)`.

### 3.5 Итоговая сложность

| Вариант | Время | Память |
| --- | --- | --- |
| С индексом `parent_id` | `O(h · log N + S · log N + k · log k)` | `O(S + k)` |
| Без индекса `parent_id` | `O(D · N + S + k · log k)`, худший случай `O(S · N)` | `O(S + k)` |

На практике при `D = 3` и умеренном `h` доминирует `S · log N` — обход
поддерева офиса.

## 4. Реальные замеры

Условия: PostgreSQL 10 в Docker, `EXPLAIN (ANALYZE, BUFFERS)`, прогретый кэш,
101 100 строк (100 офисов × 10 отделов × 100 сотрудников), поддерево офиса —
1 011 узлов, 1 000 сотрудников, целевой сотрудник `id = 558`.

| Вариант | Execution time | Оценка стоимости | План |
| --- | --- | --- | --- |
| С индексом `employees_parent_id_idx` | **1,0 мс** | 725 | `Index Scan using employees_parent_id_idx`, 3 итерации рекурсии |
| Без индекса по `parent_id` | **24,5 мс** | 22 756 | `Seq Scan on employees` (101 100 строк) × 3 итерации + `Hash Join` |

Разница — примерно **24 раза** на 100 тысячах строк. На тестовом наборе из
19 строк разница незаметна (доли миллисекунды), но она растёт линейно по `N`:
на миллионе строк запрос без индекса будет выполняться сотни миллисекунд или
секунды.

Фрагмент плана с индексом:

```text
->  Nested Loop  (actual time=0.161..0.209 rows=337 loops=3)
      ->  WorkTable Scan on office_tree t
      ->  Index Scan using employees_parent_id_idx on employees e_1
            Index Cond: (parent_id = t.id)
            actual rows=1 loops=1011
```

Фрагмент плана без индекса:

```text
->  Hash Join  (actual time=2.674..8.045 rows=337 loops=3)
      Hash Cond: (e_1.parent_id = t.id)
      ->  Seq Scan on employees e_1
            actual rows=101100 loops=3
```

## 5. Что уже сделано в решении

1. **Индекс `employees_parent_id_idx`** — главный и самый дешёвый выигрыш:
   убирает повторные сканирования таблицы.
2. **Ограничение `depth < 100`** — защита от зацикливания на некорректных
   данных (в PostgreSQL 9.6/10 нет клаузы `CYCLE`).
3. **Параметризованный запрос** — план кэшируется, SQL-инъекции невозможны.
4. **Пакетный импорт через `execute_values`** — один `INSERT` вместо 19
   отдельных вставок; для больших файлов это разница в разы.
5. **`ORDER BY id`** осознанно оставлен: сортировка `k` строк дешевле, чем
   недетерминированный порядок вывода.

## 6. Перспективы оптимизации

### 6.1 Денормализация `office_id` (лучший вариант для чтения)

Добавить в таблицу колонку `office_id` и заполнять её при импорте (и при
перемещении сотрудника):

```sql
ALTER TABLE employees ADD COLUMN office_id INTEGER;
CREATE INDEX employees_office_id_idx
    ON employees (office_id, type, id);

-- Запрос вместо двух рекурсий:
SELECT name
FROM employees
WHERE office_id = %(office_id)s
  AND type = 3
ORDER BY id;
```

- Сложность: `O(k · log N)`, рекурсии нет вообще.
- Индекс `(office_id, type, id)` отдаёт строки уже в нужном порядке — сортировка
  тоже исчезает.
- Цена: колонку нужно поддерживать в актуальном состоянии (триггер или код
  приложения), иначе данные начнут расходиться с иерархией. Для таблицы,
  которая меняется редко и читается часто, это лучший компромисс.

### 6.2 Materialized path / `ltree`

Хранить путь до узла строкой (`'1.2.12'`) или типом `ltree`
(расширение `contrib`, доступно в 9.6/10):

```sql
CREATE INDEX employees_path_idx ON employees USING GIST (path);

SELECT name FROM employees
WHERE path <@ '1' AND type = 3
ORDER BY id;
```

- Сложность: `O(k · log N)`, без рекурсии.
- Цена: при перемещении узла нужно обновлять пути всех потомков; длина пути
  ограничена.

### 6.3 Closure table

Отдельная таблица пар «предок — потомок»:

```sql
CREATE TABLE employee_closure (
    ancestor_id   INTEGER NOT NULL,
    descendant_id INTEGER NOT NULL,
    depth         INTEGER NOT NULL,
    PRIMARY KEY (ancestor_id, descendant_id)
);
```

- Поиск офиса — один индексный запрос, обход поддерева — `O(S)`.
- Цена: `O(N · h)` строк и более сложная запись (при вставке/перемещении
  добавляются/удаляются пары). Оправдано при частых перемещениях и очень
  больших деревьях.

### 6.4 Nested sets (`left`/`right`)

Поддерево выбирается одним диапазоном `left BETWEEN ... AND right` — очень
быстрое чтение. Но любая вставка или перемещение переписывает половину
таблицы. Для организационной структуры с редкими изменениями допустимо, для
частых — плохо.

### 6.5 Кэширование

Если структура меняется редко, результат можно кэшировать:

- материализованное представление «офис → сотрудники» с периодическим
  `REFRESH`;
- кэш в приложении по `office_id`.

Это убирает запрос целиком, но добавляет инвалидацию кэша. Для консольной
утилиты с одним запросом за запуск смысла нет.

### 6.6 Оптимизация импорта

- `execute_values` уже используется; для файлов в сотни тысяч строк быстрее
  `COPY ... FROM STDIN`.
- После массовой вставки стоит выполнять `ANALYZE employees`: автоанализ
  может отставать, и планировщик будет работать со старыми статистиками.
- Проверка циклов на этапе импорта позволила бы убрать ограничение
  `depth < 100` и падать с понятной ошибкой вместо «обрезанного» результата.

### 6.7 Ограничения и индексы

- Внешний ключ `parent_id → employees(id)` защитит от «висячих» ссылок
  (в текущем решении не добавлен из-за произвольного порядка импорта).
- Частичный индекс `WHERE type = 3` уменьшит размер индекса, если сотрудников
  меньшинство; но для запроса «всё поддерево» он менее полезен, чем индекс
  по `parent_id`.
- На PostgreSQL 11+ возможен covering-индекс `INCLUDE (name, type)`, который
  позволит обойтись Index Only Scan. На 9.6/10 `INCLUDE` нет; замена —
  составной индекс `(parent_id, id, name, type)`, но он заметно больше.

## 7. Рекомендации

1. **Для текущего масштаба (десятки–тысячи строк)** текущего решения с
   индексом по `parent_id` достаточно: запрос выполняется за миллисекунды.
2. **При росте до 10⁵–10⁷ строк и частых чтениях** — денормализация
   `office_id` (п. 6.1): самый простой способ убрать рекурсию и сортировку.
3. **Если важны перемещения подразделений** — materialized path или closure
   table; выбор зависит от соотношения чтений и записей.
4. **Перед любой оптимизацией** — измерить на реальных данных через
   `EXPLAIN (ANALYZE, BUFFERS)`: на малых объёмах разница может быть
   незначительной, а усложнение схемы — постоянным.

## 8. Вывод

Текущий запрос корректен и после добавления индекса по `parent_id` имеет
сложность `O(h · log N + S · log N + k · log k)`: время зависит от размера
офиса и логарифма от размера таблицы, но не от всей таблицы линейно.

Главный риск исходной версии — отсутствие индекса по `parent_id`, из-за
которого PostgreSQL сканировал всю таблицу на каждой итерации рекурсии
(подтверждено замером: 24,5 мс против 1,0 мс на 101 100 строках). Индекс
добавлен в схему.

Дальнейшая оптимизация имеет смысл только при росте данных: денормализация
`office_id` или materialized path убирают рекурсию и дают `O(k · log N)`,
ценой усложнения записи.
