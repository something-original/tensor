# Описание решения

## 1. Назначение

Консольная утилита импортирует иерархию организаций из JSON в PostgreSQL и по
идентификатору сотрудника выводит всех сотрудников офиса, в котором он работает.

Иерархия имеет три уровня:

| `type` | Сущность | `parent_id` |
| --- | --- | --- |
| `1` | офис | `NULL` |
| `2` | отдел (может быть вложенным) | офис или другой отдел |
| `3` | сотрудник | отдел |

Пример из задания: для сотрудника `id = 3` (Иванов, офис в Санкт-Петербурге)
утилита выводит `Иванов`, `Сидоров`, `Петров`.

## 2. Схема данных

```sql
CREATE TABLE IF NOT EXISTS employees (
    id        INTEGER PRIMARY KEY,
    parent_id INTEGER,
    name      TEXT NOT NULL,
    type      SMALLINT NOT NULL CHECK (type IN (1, 2, 3))
);

CREATE INDEX IF NOT EXISTS employees_parent_id_idx
    ON employees (parent_id);
```

Почему так:

- `id` — первичный ключ: поиск записи по идентификатору идёт по B-дереву,
  это нужно обоим рекурсивным запросам;
- `parent_id` — ссылка на родителя. Внешний ключ намеренно не задан: данные
  импортируются одним пакетом в произвольном порядке, а тестовый набор может
  быть неполным. Целостность проверяется при импорте (см. п. 3);
- `CHECK (type IN (1, 2, 3))` не даёт записать неизвестный тип;
- индекс по `parent_id` — ключевой для производительности: без него каждый
  шаг обхода дерева требует сканирования всей таблицы (подробно в
  [sql_complexity.md](sql_complexity.md)).

## 3. Импорт данных

Файл: `src/tensor/importer.py`.

1. JSON читается целиком (`utf-8-sig`, чтобы корректно обработать BOM).
2. Проверяется, что это массив объектов и что в каждой записи есть поля
   `id`, `Name`, `Type`.
3. Поля берутся **по именам**, а не по порядку ключей, поэтому перестановка
   ключей в JSON ничего не ломает.
4. Все строки вставляются одной командой через
   `psycopg2.extras.execute_values`:

   ```sql
   INSERT INTO employees (id, parent_id, name, type) VALUES %s;
   ```

Значения передаются как параметры, а не склеиваются в текст SQL. Это
исключает SQL-инъекции и ошибки на именах с апострофом.

Импорт выполняется только при пустой таблице. Флаг `--reset` очищает таблицу
(`TRUNCATE`) и загружает данные заново. Вся инициализация выполняется в одной
транзакции: при ошибке таблица не останется частично заполненной.

## 4. Выборка сотрудников офиса

Файл: `src/tensor/sql_commands.py`, запрос
`SELECT_COLLEAGUES_BY_EMPLOYEE_ID`.

Задача решается двумя обходами дерева в одном запросе:

```text
1. ancestors   — от сотрудника вверх по parent_id до офиса (type = 1)
2. office      — id найденного офиса
3. office_tree — от офиса вниз по parent_id по всему поддереву
4. финальный SELECT — из поддерева берутся только type = 3, сортировка по id
```

Первый обход останавливается, когда доходит до записи с `type = 1`:

```sql
WHERE a.type <> 1
```

Так офис попадает в результат, но выше него рекурсия не идёт, даже если в
данных случайно окажется родитель над офисом.

Второй обход не ограничен глубиной вложенности отделов: структура
«отдел внутри отдела» (в тестовых данных — `id = 12` и `16` внутри `11`)
обрабатывается корректно.

Защита от зацикливания: в обеих рекурсиях есть условие `depth < 100`.
В PostgreSQL 9.6/10 ещё нет клаузы `CYCLE`, поэтому глубина ограничивается
вручную. Для реальной иерархии организаций 100 уровней заведомо достаточно.

Сортировка `ORDER BY id` выбрана осознанно: она даёт тот же порядок, что в
примере задания (`Иванов`, `Сидоров`, `Петров`), и делает вывод
детерминированным.

## 5. Консольный интерфейс

Файл: `src/tensor/cli.py`.

```bash
python main.py 3              # id аргументом
python main.py                # интерактивный ввод
python main.py --reset 3      # перезалить данные и выполнить запрос
uv run tensor 3               # консольная команда после uv sync
```

Поведение:

- список сотрудников печатается в `stdout` по одному имени на строку;
- логи и ошибки идут в `stderr`, поэтому вывод можно безопасно перенаправлять
  в файл или использовать в скриптах;
- если id не найден — сообщение и код возврата `1`;
- если id существует, но это офис или отдел (`type` ≠ 3) — сообщение и код
  возврата `2`;
- ошибки подключения, чтения файла и некорректный JSON обрабатываются без
  трассировки стека: пользователь видит понятное сообщение и код `1`.

## 6. Архитектура

| Модуль | Ответственность |
| --- | --- |
| `main.py` | запуск из корня репозитория без установки пакета |
| `src/tensor/cli.py` | аргументы, ввод-вывод, коды возврата |
| `src/tensor/config.py` | настройки из переменных окружения и `.env` |
| `src/tensor/db.py` | подключение, инициализация схемы, выборки |
| `src/tensor/importer.py` | разбор JSON и пакетная вставка |
| `src/tensor/sql_commands.py` | тексты SQL-запросов |

Слой работы с БД синхронный (`psycopg2`): у консольной утилиты нет
параллельных запросов, поэтому асинхронность и веб-сервер здесь только
усложняли бы код.

## 7. Осознанные ограничения

- Нет внешнего ключа `parent_id → employees.id`: импорт рассчитан на
  произвольный порядок записей и потенциально неполные тестовые данные.
  Для продуктивной схемы внешний ключ стоит добавить.
- Нет проверки на циклы при импорте: цикл не повесит запрос благодаря
  `depth < 100`, но данные останутся некорректными.
- Повторный импорт возможен только через `--reset` (полная перезагрузка):
  частичного обновления (upsert) в задании не требуется.
